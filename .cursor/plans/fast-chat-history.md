# Быстрый показ переписки после запуска

**Статус:** шаги 2–7 выполнены. Шаг 1 (живая проверка `getChatHistory`) не выполнен: в репозитории нет учётных данных. Необязательные меры не делались.

## Проблема

После запуска чат пуст, и сообщения появляются только по мере разбора очереди уведомлений.

Почему так происходит:

- Переписка хранится только в памяти (`telegramChatStore.conversations`). После перезагрузки она пуста.
- Единственный источник сообщений — цикл `runReceivingLoop` в `TelegramChat.saga.ts`. Он строго последовательный: `receiveNotification`, затем обработка, затем `deleteNotification`, затем следующее уведомление. Каждое уведомление стоит двух HTTP-запросов подряд.
- Очередь GREEN-API хранит уведомления 24 часа. В ней лежат сообщения супергрупп, картинки, документы, сообщения с телефона и эхо API. Приложение их пропускает, но каждый пропуск тоже стоит двух запросов.
- Нужный личный текст оказывается в конце FIFO, после всего накопленного.

Почему нельзя просто ускорить цикл: пока `receiptId` не удалён, `receiveNotification` возвращает то же уведомление. Параллельные `receive` и `delete` дадут повторы и гонки. Последовательный порядок остаётся.

## Решение

Загружать историю открытого чата одним запросом [`getChatHistory`](https://green-api.com/telegram/docs/api/journals/GetChatHistory/) и не ждать очереди. Очередь продолжает работать в фоне и доставляет новые события. Пересечение истории и очереди отсекает уже существующая дедупликация по паре `chatId + idMessage` в `placeMessage`.

Что не меняется:

- данные не пишутся в `localStorage` и `sessionStorage`;
- цикл уведомлений, его владелец и порядок подтверждения остаются прежними;
- `sendMessage` не повторяется автоматически.

Ограничение: чаты, которых нет в списке, сами не появятся, пока по ним не придёт уведомление или пока чат не создадут по номеру. Получение списка чатов (`getChats`) в этот план не входит.

## Шаги

### 1. Проверить метод на живом инстансе

- `POST {apiUrl}/waInstance{id}/getChatHistory/{token}` с телом `{ "chatId": "<личный>", "count": 50 }`.
- Записать в `docs/GREEN_API_CONTRACT.md` реальный ответ: CORS, формат `idMessage` (строка), `timestamp` (секунды), `type`, `typeMessage`, `textMessage`, поведение для `extendedTextMessage`, ответ на пустой чат, код при лимите частоты.
- Добавить обезличенную фикстуру `src/shared/api/fixtures/getChatHistory.json`.
- Отдельно проверить [`getWebhooksCount`](https://green-api.com/telegram/docs/api/queues/GetWebhooksCount/) после долгого простоя. Это подтвердит размер очереди как причину задержки.

**Критерий:** формат ответа подтверждён, и `idMessage` из истории совпадает с `idMessage` того же сообщения в очереди. Без этого дедупликация не сработает.

### 2. HTTP-метод в `TelegramChat.api`

- `getChatHistory(credentials, { chatId, count }, options)` в `TelegramChat.api.ts`. Валидация через valibot, `chatId` по `CHAT_ID_PATTERN`, `count` — целое в разрешённом диапазоне.
- Типы `GetChatHistoryInput`, `ChatHistoryItem` и `GetChatHistoryResult` в `TelegramChat.api.types.ts`, с jsDoc над каждым полем.
- Константа `CHAT_HISTORY_COUNT` (например, 50) в `constants/api.ts`.
- Разбор текста по тем же правилам, что у уведомлений: `textMessage` и `extendedTextMessage`. Остальные типы отбрасываются, а не ломают ответ.
- Неизвестный элемент массива отбрасывается. Ответ не массив — `HttpClientError('invalid')`.
- Тесты в `TelegramChat.api.test.ts` на основе фикстуры.

### 3. Слияние истории с перепиской (`TelegramChat.utils.ts`)

Сейчас `placeMessage` только дописывает сообщение в конец. История приходит пачкой и состоит из более старых сообщений, поэтому нужна отдельная чистая функция `mergeHistory(conversations, chatId, items)`:

- одна запись в store на всю пачку, а не N вызовов `placeMessage`, иначе будет N перерисовок;
- пропуск элементов, чей `idMessage` уже есть в чате;
- исходящее из истории связывается с локальным `pending`/`failed` без `idMessage` по тексту, как `findPendingOutgoing`. Логику переиспользовать, не дублировать;
- сортировка по `sentAt`, при равенстве сохраняется существующий порядок;
- статус сообщений из истории — `accepted`.

Тесты: пустой чат, пересечение с очередью, эхо локального `pending`, порядок, повторная загрузка не меняет ссылку на массив.

### 4. Saga и состояние загрузки

- `telegramChatSaga.loadChatHistory` на `reatomAsync` с `withAbort()` (`last-in-win`): быстрое переключение A→B отменяет запрос A. `reatomResource` не используется. Так модель остаётся единообразной, а запись идёт в общий `conversations`, а не в кэш ресурса.
- Перед записью проверяются поколение сессии (`sessionMoved`) и `ctx.controller.signal.aborted`.
- Ошибки переводятся в безопасный текст по образцу `toCreateChatError`, без токена.
- В store добавляется атом `historyByChat: Record<chatId, 'loading' | 'loaded' | 'failed'>`. Он очищается в `clearSessionData`.
- Чат со статусом `loaded` повторно не запрашивается в той же сессии.

### 5. Запуск загрузки

- `selectChatAction` после смены выбора запускает `loadChatHistory`, если для этого чата ещё нет `loaded`.
- `createChatAction` получает это поведение через `selectChatAction`, отдельного вызова не нужно.
- Цикл уведомлений не трогается.

### 6. UI

- В `useTelegramMessages` добавить `historyStatus` выбранного чата, тип описать в `useTelegramMessages.types.ts`.
- `ChatWindow`: пока статус `loading` и сообщений нет, показывать «Загружаем переписку…» вместо «Переписка пуста». При `failed` — короткий текст и кнопка «Повторить».
- Не ставить `memo`, `useCallback` и `useMemo` без измеренной причины.

### 7. Документация

- `README.md`: вместо «обработанная история не восстанавливается» описать, что переписка открытого чата подгружается из журнала GREEN-API.
- `docs/ARCHITECTURE.md`: новый раздел о `loadChatHistory`, его стратегии отмены и связи с очередью.
- `IMPLEMENTATION_PLAN.md`: отметка о шаге.

## Необязательно, после замера

- **Сброс накопленной очереди при подключении** выполнен: в начале цикла один раз вызывается `clearWebhooksQueue`. Чаты из очереди не создаются, текст пишется только в чат, открытый по номеру. `getChats` не добавлялся.
- **Отключить лишние типы уведомлений** через `setSettings`, например `outgoingMessageWebhook` для сообщений с телефона. Это уменьшит очередь, но меняет настройки инстанса. Сначала нужно согласовать.
